## 2. Classification

**Classification**: Custom hardware-fingerprint-gated dropper / "fake activation" loader impersonating PDF-XChange Editor.
**Confidence**: High (behavior fully reconstructed from .NET IL disassembly; confirmed inert-without-key behavior via dynamic sandboxing).
**Family attribution**: None. KesaKode (both offline pre-computed and online authoritative lookup via KesaKode cloud API) returned **zero verdict matches** — no code overlap with any tracked family in the KesaKode database. This is not a known/tracked family; treat as a standalone/novel sample.

**Reasoning**: The binary's entire logic is a self-contained "product activation" gate. It is not a generic PUP installer — it deliberately computes a machine-bound value that only someone possessing an embedded secret string can solve, then uses the operator-supplied response to decrypt and launch a second-stage payload that is not present in this file. This "collect machine ID → attacker computes code out-of-band → victim enters code → payload unlocks" flow is a deliberate anti-sandbox / targeting mechanism, not standard software licensing (the code is derived from an embedded static string, not a real license server).

## 3. Capabilities

- **Hardware fingerprinting**: queries `SELECT SerialNumber FROM Win32_DiskDrive` via WMI (`System.Management`) to obtain a unique machine identifier (falls back to literal string `FALLBACKDISKID` if WMI query returns nothing).
- **Fake license/activation UI**: displays a WinForms dialog (Chinese-language, "产品商业授权中心" / "Product Commercial Authorization Center") showing the victim a formatted "machine code" (first 6 + `-` + next 6 hex chars of `MD5(disk_serial)`), and prompts for an "activation code."
- **Deterministic code validation without network callback**: the expected code is `Base64(SHA256(hwid_hash + "InspirationEvolution_2026"))` — computed entirely locally; there is no C2 callout to validate the code, meaning the operator must compute the correct code out-of-band (e.g., from the victim reporting their code via phone/chat) and supply it back.
- **Conditional payload unlock**: on correct code entry, decrypts `settings.dat.enc` → `settings.dat` using AES (key = `SHA256("PackKey_Secret_" + "InspirationEvolution_2026")`, IV = first 16 bytes of the encrypted file), persists the entered code to `license.lic` for future runs (skips the dialog if `license.lic` already contains the valid code).
- **Second-stage execution**: if `pluginscache.exe` exists alongside the dropper, marks `settings.dat` hidden+system, launches `pluginscache.exe` (waits for exit), then restores `settings.dat` attributes to normal and deletes it.
- **Persistence**: creates `PDFXEdit.lnk` on the user's Desktop via `WScript.Shell` COM automation, pointing back at its own executable path (icon = base directory) — re-launching the same activation-gate flow on each click.
- **Social-engineering distraction**: prompts the user (Chinese language) to set PDFXEdit as the default PDF handler via `ms-settings:defaultapps`, reinforcing the "legitimate software" cover story.
- **Anti-analysis by design**: because the unlock code cannot be derived without knowing the embedded secret and the victim's disk serial, no code is currently known to sandboxes/analysts — the malicious decrypt+launch path is unreachable without operator interaction, effectively defeating automated dynamic analysis (confirmed empirically in Section 6).

capa/MBC mapped techniques: T1027 (Obfuscated Files/Information — the AES-encrypted stage), T1083 (File and Directory Discovery), T1047 (WMI), T1547.009 (Shortcut Modification persistence), T1222 (file permission/attribute modification), T1620 (Reflective Code Loading — flagged for the `Activator.CreateInstance`/`InvokeMember` COM automation pattern, which is a false-positive-prone heuristic here; it corresponds to the WScript.Shell shortcut creation, not code injection).

## 4. Attack Chain

1. Victim receives/runs `PDFXEdit.exe` (likely delivered alongside `settings.dat.enc`, `pluginscache.exe`, in the same directory — neither companion file was present in this submission).
2. On first run: creates a desktop shortcut, computes disk-serial-derived "machine code," displays fake activation dialog.
3. Victim is expected to relay the displayed machine code to the operator (out of band — phone, chat, forum, etc.) — this is the human-in-the-loop targeting/gating step.
4. Operator computes the matching activation code offline (knowing the embedded secret `InspirationEvolution_2026`) and returns it to the victim.
5. Victim enters the code → validated locally → `settings.dat.enc` is AES-decrypted to `settings.dat` and stored → `license.lic` written to skip the dialog on future runs.
6. If `pluginscache.exe` is present, it is launched with `settings.dat` as a hidden/system companion file (contents/purpose unknown — not recovered in this analysis).
7. Prompts victim to set the fake app as the default PDF handler, deepening the disguise.

## 6. Emulation Results

Native emulation (speakeasy/angr) was not applicable — this is a pure .NET IL assembly with no native decrypt/obfuscation routines; the entire control flow (WMI query → hash → dialog → AES decrypt → process launch → shortcut creation) was fully and unambiguously recovered via direct .NET IL disassembly (`fn_disassemble` on all 6 functions in the assembly: `DotNetEntryPoint`, `CreateShortcutDynamic`, `DecryptFile`, the `<Main>b__5` event handler, and two constructors). FLOSS confirmed it does not support .NET string deobfuscation (expected/non-issue, since no strings are obfuscated — all relevant strings are visible in cleartext, as reflected in the stringsifter ranking).

## 8. Analyst Notes

- **Payload gap**: `settings.dat.enc` and `pluginscache.exe` — the actual malicious payload and its encrypted configuration — were not included in this submission and were not recoverable from this file alone. If these companion files become available, the AES key derived here (`SHA256("PackKey_Secret_InspirationEvolution_2026")`) will decrypt `settings.dat.enc` directly.
- **Targeting model**: The "victim reports machine code, operator computes response" flow implies this is used in a semi-manual, likely small-scale or targeted distribution campaign (e.g., via a chat/forum-based "activation support" channel), rather than mass/automated delivery — consistent with the complete absence of any KesaKode code-sharing hits (a widely distributed toolkit would more likely show matches).
- **Recommended follow-up**: If `pluginscache.exe` or `settings.dat.enc` are recovered from the same distribution point/victim host, re-run this pipeline against them using the recovered AES key. Also worth monitoring for reuse of certificate serial `320f566c4a48d5133d628a72` on future submissions, given its prior appearance on `minibrowser.exe`.
- **Alternative hypothesis considered and rejected**: this could theoretically be legitimate software-licensing code reused by a copycat; however, the local-only code derivation (no license server, no online validation), Chinese-language "authorization center" lure text, disguised PDF-X Editor branding with mismatched real product identity, and companion-file-driven secondary execution collectively rule out benign licensing software.
